# LAN Voice Chat

تطبيق ويب للدردشة النصية والمكالمات الصوتية (ثنائية وجماعية) داخل شبكة
محلية (LAN) واحدة، بدون أي اتصال إنترنت بعد تشغيل السيرفر.

---

## 1. التشغيل السريع

```bash
cd LAN-Voice-Chat
pip install -r requirements.txt

cd backend
python run.py
```

سيظهر شيء مثل:

```
============================================================
  LAN Voice Chat — HTTPS
  من نفس الجهاز:      https://127.0.0.1:8443
  من أجهزة الشبكة:    https://192.168.1.10:8443
  ملاحظة: المتصفح سيُظهر تحذير 'اتصال غير آمن' لأن الشهادة
  ذاتية التوقيع — هذا متوقع، اضغط 'متابعة/Advanced' لتجاوزه
  (مرة واحدة فقط لكل جهاز/متصفح).
============================================================
```

افتح رابط `https://<IP>:8443` من أي جهاز على نفس شبكة الـ Wi-Fi، وتجاوز
تحذير الشهادة (خطوة لمرة واحدة لكل جهاز — التفاصيل بالأسفل).

> ⚠️ تأكد أن جدار حماية جهاز السيرفر يسمح بالمنفذ 8443.

## 2. حل مشكلة "الاتصال" وطلب الميكروفون (الأهم)

هذا هو التصحيح الذي طلبته: المتصفحات (خصوصًا الجوال) **تمنع الوصول
للميكروفون تمامًا من أي رابط http عادي** غير `localhost`. بما أن كل جهاز
غير جهاز السيرفر نفسه يدخل عبر IP الشبكة (وليس localhost)، فالحل الوحيد
هو HTTPS.

**ما أضفناه:**
- `backend/certs.py`: يولّد شهادة HTTPS ذاتية التوقيع تلقائيًا (عبر أداة
  `openssl` الموجودة على أغلب الأنظمة) في كل مرة يشتغل فيها السيرفر،
  متضمنة IP جهاز السيرفر الحالي.
- `backend/run.py`: يشغّل uvicorn مع هذه الشهادة تلقائيًا على المنفذ 8443.

**تجربة فعلية أجريتها هنا:** ولّدت شهادة تجريبية وتحققت أنها تحتوي على
IP و`localhost` ضمن Subject Alternative Name بشكل صحيح (هذا الحقل إلزامي؛
بدونه يرفض المتصفح الشهادة برسالة `ERR_CERT_COMMON_NAME_INVALID` حتى لو
كانت الشهادة "صحيحة" شكليًا). لم أستطع تجربة الاتصال HTTPS الفعلي عبر
uvicorn لعدم توفر إنترنت لتثبيت المكتبات في بيئتي (التفاصيل في قسم 8).

### كيف تتجاوز تحذير "اتصال غير آمن"؟
هذا متوقع تمامًا مع أي شهادة ذاتية التوقيع (غير صادرة من جهة موثوقة عالميًا)
ولا يوجد حل بديل حقيقي بدون شراء نطاق ودخول الإنترنت لإصدار شهادة حقيقية.
لكل متصفح، مرة واحدة فقط لكل جهاز:

- **Chrome/Edge (أندرويد وويندوز)**: اضغط "Advanced" ثم "Proceed to ... (unsafe)"
- **Safari (آيفون/ماك)**: اضغط "Show Details" ثم "visit this website"
- **Firefox**: اضغط "Advanced" ثم "Accept the Risk and Continue"

## 3. المحادثات الجماعية (نص + صوت) — جديد

### قاعدة البيانات (الجداول المضافة)
- `groups`: اسم المجموعة ومنشئها.
- `group_members`: عضوية كل مستخدم في كل مجموعة.
- `group_messages`: سجل الرسائل النصية الجماعية.
- `group_calls` و `group_call_participants`: سجل تاريخي لمكالمات المجموعة
  (متى بدأت/انتهت، من شارك ومتى غادر).

### كيف تعمل المكالمة الجماعية تقنيًا (Mesh)
لا يوجد خادم وسيط يعالج الصوت (SFU)؛ بدل ذلك، **كل مشارك يفتح اتصال WebRTC
مباشر مع كل مشارك آخر** في نفس المكالمة. عند انضمام شخص جديد:

1. يرسل للسيرفر `group_call_join`.
2. السيرفر يرد عليه بقائمة المشاركين الحاليين (`group_call_roster`).
3. المنضم الجديد يبدأ اتصال WebRTC (Offer) مع كل واحد منهم.
4. كل طرف موجود مسبقًا يستقبل هذا العرض ويرد تلقائيًا (بدون "رنين" — لأن
   الموافقة الفعلية حصلت لحظة انضمامهم هم أنفسهم للمكالمة).

هذا الأسلوب (Mesh) ممتاز على شبكة محلية لعدد صغير (حتى ~6-8 أشخاص)، لأن
النطاق الترددي للشبكة المحلية عالٍ جدًا. لأعداد أكبر بكثير، يحتاج المشروع
خادم توزيع وسائط (SFU) مثل mediasoup أو LiveKit — بنية أثقل بكثير تحتاج
مكتبات إضافية واختبارًا موسّعًا، وهي خارج نطاق مشروع دراسي يعمل بدون إنترنت.

### الاستخدام من الواجهة
- زر "+ جديدة" في قسم "المجموعات" بالقائمة الجانبية لإنشاء مجموعة.
- افتح المجموعة وأرسل رسائل نصية بشكل طبيعي.
- زر 🎙️ بالأعلى يبدأ مكالمة جماعية وينبّه كل الأعضاء ببانر دعوة.
- شريط سفلي يظهر أثناء المكالمة الجماعية (لا يحجب الشاشة) لعرض المشاركين
  والكتم/المغادرة.

## 4. تحسينات الكفاءة

| قبل | بعد | الأثر |
|---|---|---|
| فتح اتصال SQLite جديد مع كل استعلام | اتصال واحد مشترك يُفتح عند الإقلاع فقط | إزالة كلفة فتح/إغلاق الملف في كل طلب |
| بدون فهارس صريحة | فهارس على `messages(sender_id, receiver_id)` و`group_messages(group_id)` | استعلامات سجل المحادثات أسرع مع نمو البيانات |
| ردود HTTP بدون ضغط | `GZipMiddleware` مفعّل | حجم أصغر لسجلات الرسائل الطويلة |
| WAL غير مفعّل | `PRAGMA journal_mode=WAL` | قراءة/كتابة متزامنة أفضل مع عدة مستخدمين |

## 5. تشغيل السيرفر من الجوال (بدون لابتوب) — بصراحة كاملة

### ✅ أندرويد: ممكن فعليًا عبر Termux

1. ثبّت **Termux** من [F-Droid](https://f-droid.org/packages/com.termux/)
   (وليس من Google Play — النسخة هناك قديمة ومهجورة).
2. داخل Termux:
   ```bash
   pkg update && pkg upgrade
   pkg install python openssl-tool git
   ```
3. انقل مجلد المشروع للجوال (عبر `git clone` لو رفعته لمستودع، أو عبر نقل
   ملفات مباشر) ثم:
   ```bash
   cd LAN-Voice-Chat
   pip install -r requirements.txt
   cd backend
   python run.py
   ```
4. الجوال الآن هو السيرفر. بقية الأجهزة (جوالات/لابتوبات) تتصل بعنوان IP
   الجوال الذي سيظهر في الطرفية، بالضبط كما لو كان لابتوب.
5. **مهم**: أندرويد يوقف التطبيقات في الخلفية لتوفير البطارية، ما قد يقتل
   عملية Termux إذا خرجت من التطبيق. شغّل الأمر التالي في جلسة Termux قبل
   `python run.py` لمنع ذلك أثناء الاستخدام:
   ```bash
   termux-wake-lock
   ```

### ❌ آيفون (iOS): غير ممكن كسيرفر بدون Jailbreak

هذا تصحيح صريح لازم أذكره: نظام iOS **لا يسمح لأي تطبيق عادي (من App Store)
بتشغيل خادم شبكة يستمر بالعمل في الخلفية** بهذه الطريقة — هذا قيد أمني
أساسي في iOS نفسه وليس نقصًا في هذا المشروع. لا توجد طريقة موثوقة وقانونية
لجعل آيفون "سيرفر" لهذا التطبيق بدون Jailbreak (وهو غير مستحسن أصلًا).

**آيفون يعمل بشكل ممتاز كـ Client (عميل)**: يفتح Safari ويستخدم التطبيق
بكل ميزاته (نص + صوت + مكالمات جماعية) بشرط أن يكون السيرفر يعمل على جهاز
آخر (لابتوب، أو جوال أندرويد عبر Termux، أو Raspberry Pi... إلخ).

### ملخص الجدول

| الجهاز | سيرفر؟ | Client؟ |
|---|---|---|
| لابتوب/كمبيوتر (Windows/Mac/Linux) | ✅ | ✅ |
| جوال أندرويد (عبر Termux) | ✅ | ✅ |
| آيفون / آيباد | ❌ | ✅ |

## 7. بروتوكول WebSocket (محدَّث)

### من العميل إلى السيرفر

| type | الحقول | الوصف |
|---|---|---|
| `chat_message` | `to`, `message` | رسالة ثنائية |
| `group_message` | `group_id`, `message` | رسالة جماعية |
| `call_offer` | `to`, `sdp`, `group_id`? | عرض WebRTC (ثنائي أو جزء من Mesh) |
| `call_answer` | `to`, `sdp` | رد WebRTC |
| `ice_candidate` | `to`, `candidate` | تبادل ICE |
| `call_reject` / `call_end` | `to` | إنهاء/رفض مكالمة ثنائية |
| `group_call_invite` | `group_id` | دعوة كل أعضاء المجموعة لمكالمة |
| `group_call_join` | `group_id` | انضمام فعلي للمكالمة الجماعية |
| `group_call_leave` | `group_id` | مغادرة المكالمة الجماعية |

### من السيرفر إلى العميل (الإضافات الجديدة)

| type | الوصف |
|---|---|
| `group_message` | رسالة جماعية واردة |
| `group_call_incoming` | دعوة لمكالمة جماعية (بانر) |
| `group_call_roster` | قائمة من يجب الاتصال بهم عند الانضمام |
| `group_call_participant_joined` / `_left` | تحديث حيّ لقائمة المشاركين |

## 8. تنبيه هام: حدود الاختبار في بيئتي

بيئة العمل هنا **بدون اتصال إنترنت**، لذلك:

- ✅ اختبرت فعليًا: توليد شهادة HTTPS بالكامل (openssl) والتحقق من محتواها.
- ✅ اختبرت فعليًا: منطق قاعدة البيانات الجديد (الجداول، الفهارس، استعلامات
  المجموعات) عبر sqlite3 القياسية مع بيانات وهمية.
- ✅ فحصت: صحة صياغة كل ملفات Python (`py_compile`) وJavaScript (`node --check`)،
  وتطابق كل معرّفات HTML/JS.
- ❌ لم أستطع: تثبيت `fastapi`/`uvicorn`/`aiosqlite` وتشغيل السيرفر الفعلي
  كاملًا، ولا تجربة اتصال WebRTC حقيقي بين جهازين، بسبب عدم توفر إنترنت
  لتنزيل المكتبات.

جرّبه عندك وأخبرني بأي رسالة خطأ فعلية تظهر — أغلب الاحتمال أخطاء صغيرة
(اسم متغير، نسخة مكتبة) يسهل تصحيحها فورًا عند رؤيتها.

## 9. قيود معروفة

- Mesh محدود عمليًا بعدد صغير من المشاركين بالمكالمة الجماعية (~6-8).
- جلسة دخول واحدة فقط لكل مستخدم في نفس الوقت (تسجيل دخول جديد يُلغي القديم).
- التوكنات في الذاكرة: تُمسح عند إعادة تشغيل السيرفر.
- لا فيديو حاليًا (البنية تسمح بإضافته: `getUserMedia({video: true})`).
- iOS لا يمكنه العمل كسيرفر (انظر قسم 5).
